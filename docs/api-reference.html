The catch — read before designing around volumes

Across 41 metered machines and 34 meters in this sandbox, every average volume field is 0.0. The demo database never accumulated the reading history those averages are derived from — only 23 of 100 equipment records even carry a most-recent reading.

And there is no meter-reading history endpoint. You can PUT AddMeterReading to write one, and read a single mostRecentDefaultMeterReadingDisplay off each equipment record, but nothing lists readings over time. So where the averages are zero you cannot compute them yourself from this API — the raw series is not exposed.

Whether that is a sandbox artifact or a production reality is the one thing worth confirming against a live dealer database before you build reporting on it. PrintReleaf is the fallback that does return real page counts today.

Worth knowing before you go asking for more claims

The ListsAndCodes block looks like losing every lookup table. It isn't. Each list is duplicated under a domain-scoped route gated on the domain claim instead — /api/ListsAndCodes/CallTypes is 403 while /api/ServiceCall/CallTypes returns the same 26 rows. All 19 have a working twin, so nothing is genuinely missing here.

The real gaps are /api/User/* (no technician or sales-rep roster) and /api/Branch. Equipment and calls reference technicianId and branchId, so without those routes you get IDs you cannot resolve to names. That is the one thing worth requesting.

04ID136 and ID634

Your two process IDs, and what they actually map onto.

ID136 — API sync to ticketing systems

Not an endpoint. It is the CEO Juice process behind the ServiceCall routes: AddCall, AddNote, CancelCall (valid only before a technician is dispatched), ByCallNumber, AllOpen, Recentchanges. Either serialNumber or equipmentNumber is required — that is what binds a call to a machine. Put your own ticket ID in referenceCallIdentifier so calls reconcile back later.

ID634 — sales order import

The complicated one, and it earns the label. PUT /api/SalesOrder/AddOrder is not a plain create — it stages one row per order line into ZCJ_ImpSOOrderDetails under a shared SourceID, then runs ZCJ_Event_634_Log, which derives the header from the batch and writes the resulting SOID back onto the staged rows.

The failure mode nobody warns you about

The DTO has 103 fields with no required markers, mixing line-level (item, qty, unitPrice) with header-level (impCustomerNumber, poNumber, soDate, shipTo*, termsCode) in one flat shape.

Because the procedure reads header values off the batch rather than per line, inconsistent header fields across lines do not raise a validation error — the header is simply built from whichever row wins. Silent wrong data, not a failed request. Repeat header values identically on every line.

05Two gotchas that would bite a sync job

Recentchanges caps at 7 days — and exceeding it is not an error

/api/{Entity}/Recentchanges/{sinceTime} honours a 7-day window. Ask for 30 days back and you get {"totalCount":0,"items":[]} with HTTP 200 — indistinguishable from "nothing changed". A nightly job that misses a week would conclude the dataset is clean and skip every real update.

Equipment numbers contain spaces

Real values look like EQ100023 Dept 330. Interpolating one straight into a URL path throws before the request is even sent. Percent-encode every path segment — it bit us mid-probe.
