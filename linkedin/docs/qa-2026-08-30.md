## Severity 1 — writes wrong facts about real people, or over-sends

### 1.1 An unparseable end date turns a departed employee into a current one

`verify.Role.is_current` is `end is None`. `parse_li_date` returns `None` for
anything it cannot parse — and it only accepts `%m/%d/%Y`, `%m/%Y`, `%Y`.
LinkedIn also emits forms like `"Jan 2023"`.

```python
{"company": "Acme Corp", "position": "VP Sales",
 "start": "1/1/2019", "end": "Jan 2023"}     # they LEFT in Jan 2023
```

```
end parsed as: None -> is_current: True
verdict:   yes
evidence:  current role 'VP Sales' at 'Acme Corp' (from 2019-01-01, no end date)
tenure:    7.7   confident: True
```

The verdict is `yes`, the evidence string asserts "no end date" as fact, and
tenure is fabricated from a role that ended three years ago. A rep dials the
old employer — the precise outcome this program exists to prevent.

`parse_li_date`'s own docstring says an unparseable date "is a reason to treat
a profile as unreadable, never to call someone a mover." The code does the
opposite, and in the more damaging direction.

**Fix:** distinguish *absent* `end` from *present-but-unparseable*. Absent →
current. Unparseable → `unreadable`, never `yes`.

### 1.2 The `moved` destination company is whichever role happens to be first

`verify_employment` sets `destination = current[0].company`. The module
docstring states plainly that entries are **not** in chronological order.

```python
current roles: [Board Member @ Riverside Youth Baseball (2018-),
                Chief Revenue Officer @ Globex (2024-)]
CRM company:   Acme Corp (ended 2024-05-01)
```

```
verdict:   moved
evidence:  role at 'Acme Corp' ended 2024-05-01; now at 'Riverside Youth Baseball'
```

A `moved` verdict drives **re-association to the real employer**. This
re-associates a CRO to a youth baseball board seat and writes it to the CRM as
evidence.

**Fix:** rank the current-role set — most recent `start` wins, and prefer a
role whose title carries a `SENIOR_TITLE_TOKENS` term over one that does not.
Where the set is genuinely ambiguous, queue it rather than pick.

### 1.3 The cap fails OPEN in the exact window it was built for

`decide_allowance` halts on a stale ledger only when
`ledger_writes_ever > 0 and ledger_writes_in_window == 0`. After
`LEDGER_EPOCH`, "ledger broken since the epoch" and "fresh ledger, nothing
sent yet" are the same state — `ever == 0` — and the guard does not fire.

```
run 2, ledger totally dead, no independent count:
   halted    = False
   allowance = 20
   reason    = 20 allowed (0/60 used today)
```

So: the routine sends 20, every task write fails silently, the next run reads
zero and sends 20 more. Indefinitely. This is the 2026-06-01 failure verbatim.

The guard that *would* catch it is the `independent_count` reconciliation —
which is an **optional keyword argument defaulting to `None`**. The
fail-closed guarantee is therefore opt-in, in the one module whose docstring
says "every path here fails CLOSED".

```
same call, with independent_count=20:
   halted = True | ledger says 0 today but an independent count says 20
```

**Fix:** make `independent_count` required. A caller that cannot obtain a
second opinion should have to pass that fact explicitly and be halted, not
silently granted full capacity.

### 1.4 `write_back` reports success it never verified

```python
_request("POST", "/crm/v3/objects/contacts/batch/update", token,
         {"inputs": updates[i:i + 100]})
written += len(updates[i:i + 100])
```

The response is discarded. HubSpot's batch endpoints return **207 Multi-Status**
with per-input errors and a `status` of `PARTIAL`; `urllib` treats 207 as
success, so a batch where half the inputs failed reports every input written.

A uniqueness conflict on `linkedin_profile_url__unique_value` — the very key
this script writes — surfaces exactly this way.

This is the same shape as the failure the whole repository exists to fix: a
routine reporting success while writing nothing.

**Fix:** read the response, count `results`, surface `errors` and any
non-`COMPLETE` status into `rejected`.

## Severity 2 — halts a healthy run

### 2.1 Thirty-one of fifty-five Unipile error codes are unclassified

Diffed `errors.py` against the full error enum in Unipile's OpenAPI spec:

```
31 of 55 spec errors are unclassified  ->  all fall through to HALT
```

HALT-by-default is the right *default* — an unknown failure on a live account
is not something to guess through. But eleven of these are ordinary
per-candidate conditions that should be `SKIP`, and one is on the engagement
routine's critical path:

| slug | HTTP | current | should be |
|---|---|---|---|
| **`comments_disabled`** | 422 | HALT | SKIP — one post with comments off ends the whole run |
| `user_unreachable` | 422 | HALT | SKIP |
| `blocked_recipient` | 422 | HALT | SKIP |
| `no_connection_with_recipient` | 422 | HALT | SKIP |
| `not_allowed_inmail` | 422 | HALT | SKIP |
| `cannot_resend_yet` | 422 | HALT | SKIP |
| `cannot_resend_within_24hrs` | 422 | HALT | SKIP |
| `action_already_performed` | 422 | HALT | SKIP, `log_anyway=True` |
| `cannot_invite_attendee` | 422 | HALT | SKIP |
| `insufficient_credits` | 422 | HALT | STOP_FOR_DAY |
| `no_handler` | 503 | HALT | RETRY |
| `unexpected_error` | 500 | HALT | RETRY (bounded) |

### 2.2 Two slugs in our sets do not exist in the API

```
BENIGN:    'already_invited'     — invented; the real slug is already_invited_recently
SKIPPABLE: 'cant_resend_yet'     — typo for  cannot_resend_yet
```

`cant_resend_yet` means the condition it was written to skip currently HALTs.

## Severity 3 — stale constants that contradict live reality

### 3.1 `DUPLICATE_ACCOUNT_TO_DISCONNECT` names the account v2 depends on

```python
DUPLICATE_ACCOUNT_TO_DISCONNECT = "7lBoyXuETqKdiJYLj5HBGA"
```

Live v2 account detail:

```
acc_01m19mb99wfzvsb68etkn5n87x
  metadata.v1_account_id  7lBoyXuETqKdiJYLj5HBGA
```

Following this instruction disconnects the account v2 maps to. The comment
also asserts "no code may reference it" while `config.SHAWN_ACCOUNT_ID` pins
the *other* one — so the two Shawn accounts are split across the two API
versions. Both are live; both return his 7 dated roles. **One must be chosen
and the other deleted before anything sends** — two live sessions on one
LinkedIn member is a documented Unipile error (`errors/multiple_sessions`),
which `errors.FATAL` already treats as page-a-human.

### 3.2 `UNIPILE_BASE` is the unreachable form

```python
UNIPILE_BASE = "https://api30.unipile.com:16072/api/v1"
```

Port-in-host, which this environment cannot reach — the bug that kept both
routines dark for twelve weeks. Dead (nothing imports it), but it is the first
thing a reader looking for the base URL will find. `unipile.base_url()` is the
live one.

### 3.3 Sixteen dead constants, two of them contradicting live behaviour

Nothing outside `config.py` imports any of these:

```
UNIPILE_BASE  DUPLICATE_ACCOUNT_TO_DISCONNECT  SHAWN_PUBLIC_IDENTIFIER
UNIPILE_BENIGN  UNIPILE_RETRYABLE  UNIPILE_STOP_FOR_DAY  UNIPILE_HARD_STOP
UNIPILE_USAGE_STOP_THRESHOLD  SELF_COMMENTS_PATH  POSTS_REQUIRE_PROVIDER_ID
PROFILE_SECTIONS_PARAM  POST_TIMESTAMP_FIELD  SKIP_REPOSTS
COMMENT_SELF_MATCH_FIELD  SKIP_ON_PENDING_INVITATION  post_join_key
```

Two matter more than the rest:

- **`UNIPILE_BENIGN/RETRYABLE/STOP_FOR_DAY/HARD_STOP` disagree with
  `errors.py`.** config lists 2 retryable slugs, `errors.py` lists 6; config
  lists 4 fatal, `errors.py` lists 12. Two sources of truth for the most
  safety-critical classification in the system, and the dead one is the wrong
  one.
- **`PROFILE_SECTIONS_PARAM = "experience"`** documents the single most
  dangerous parameter in the program — and is dead. The live default is a
  hardcoded literal in `unipile.profile(..., sections="experience")`. Change
  the constant and nothing happens.

`config.post_join_key` also duplicates `posts.post_join_key` **without its
None guard** — `config`'s version raises `AttributeError` on `None` where
`posts`' returns `None`. `posts`' is the live one. Same for `NICKNAMES`:
config has 12 entries, `normalize.py` has 45, and `normalize`'s is the one
used.

### 3.4 `ROUTINE.md` states two things that are no longer true

- line 35: *"all Unipile calls go through the Unipile MCP, never curl"* —
  false since the `?port=` fix. This is the contract document; an agent

- line 59: *"Sales Navigator is currently unusable through Unipile"* — true on

## What is genuinely sound

  on a missing `work_experience` key caught the v2 migration live and stopped
  every contact being scored as a mover.

  behaviour is correctly characterised, and the skip-don't-guess rule on
  conflicting URLs is right.

  handled by `zoneinfo` rather than a hardcoded offset.

  denylist is correct and the constant is load-bearing.

  rather than per-post, and refuse a partially-paged set.
- **Preflight's schema checks** caught the `hs_lead_status` label-vs-value bug
  and the `ai__sources_confirming` type, and both still pass live.

## Two things deliberately NOT changed

**Which of Shawn's two v1 accounts survives.** Both are live and both work.
Disconnecting one is an action on his LinkedIn, and the earlier config was
wrong precisely because it encoded that guess. `check_send_account` now
reports the split on every preflight; the decision stays with him.

**The `moved` ranking heuristic is a heuristic.** Seniority-then-recency is
right for the board-seat-versus-CRO case that motivated it. It is not proven
against the portal's real distribution of multi-role contacts. The
`destination_ambiguous` flag exists so the uncertain cases queue instead of
guessing, but the ranking itself should be re-checked once the routine has
produced its own run history.

# Follow-up, same day: the v2 key was there all along

Shawn pointed out that v2 shows only one account for him, and that the
environment already holds the v2 key. Both true, and re-verified live:

```
V2   1 Shawn account   acc_01m19mb99wfzvsb68etkn5n87x   running
V1   2 Shawn accounts  7lBoyXuETqKdiJYLj5HBGA  2026-05-10  MESSAGING OK
                       S6ua4SfUT4SMRFZFOmyUzQ  2026-03-09  MESSAGING OK
```

**The key was stored as `UNIPILE_V2_KEY`. The code read
`UNIPILE_V2_API_KEY`.** Nothing raised. `UnipileClient` reported "no v2 key
configured" and degraded every call to the v1 fallback — so the v2 migration
would have looked complete while nothing routed to v2, and preflight's new
account check reported SKIPPED rather than running. `v2_key_from_env()` now
accepts either name, and the mismatch is pinned by tests.

**The duplicate is v1-only, and the code was pointed at the wrong half.**
v2 lists one Shawn and maps it to `7lBoyXuETqKdiJYLj5HBGA`, while
`SHAWN_ACCOUNT_ID` pinned `S6ua4SfUT4SMRFZFOmyUzQ` — so the primary transport
and the fallback would have driven two different LinkedIn sessions for one
person, which is what produces `errors/multiple_sessions`. `SHAWN_ACCOUNT_ID`
is now aligned to v2's mapping. Disconnecting the stale v1 record is
housekeeping and blocks nothing.

Preflight now reports, live:

```
[PASS] send_account: v1 and v2 agree on 7lBoyXuETqKdiJYLj5HBGA,
       member ACoAAAGv8WABzhfWcURPIaBDzbgiEWX5e781Etw
```

## A test-isolation defect this surfaced

Reading the environment inside `UnipileClient` meant the "no key configured"
tests picked up the real key and made live HTTP calls to Unipile — a unit
suite silently acquiring a dependency on the network and on someone's
credentials. An autouse fixture now clears both names. Verified by running
the suite with every credential unset: 332 passed.
