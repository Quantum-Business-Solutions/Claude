# Blog QA — heading fix verification + site sweep, 27 Sep 2026

## Heading capitalization fix: confirmed live, holding on all 71 posts

Crawled every published Praxera blog post with a real browser (Playwright/Chromium) and read the
computed CSS on every `<h2>` inside the article body. Result: **71 of 71 posts show
`text-transform: uppercase` on every h2, and zero h3s were affected** (FAQ questions, "Key
Takeaways", "Related Content" all stayed in their original case, as intended). HubSpot's CDN cache
has fully caught up since the push.

## Two other issues found, unrelated to the heading fix

### 1. Font Awesome icon kit returns 403 — sitewide, both properties, pre-existing

`kit.fontawesome.com/5e60ff1772.js` — the script that loads the site's icon font — returns
**403 "Not allowed when Origin missing"**. Confirmed this happens identically on
`blog.davincilabs.com` today, so it isn't something the Praxera rebuild broke; the Kit itself
(likely its domain allowlist or the account behind it) is the problem, and it's been broken at
the source for a while now.

**Visible effect:** the mobile hamburger menu icon and the mobile nav's dropdown carets render as
nothing — blank space next to the logo — on every page, on phone-width screens. Confirmed on both
a blog post and the home page. Screenshots sent separately.

This needs whoever owns the Font Awesome Kit account (not something fixable via the HubSpot API)
to check the kit's status and its allowed-domains list.

### 2. One dead image, one post

`/blog/how-to-sell-supplements` — the first image in the article body, `Praxera.LitX (2).png`,
404s. Confirmed with a direct request (not a rendering fluke). Displays as a broken-image icon +
alt text to visitors right now. Checked all 70 other posts for the same filename — isolated to
this one post, not a shared graphic.

## False alarm, ruled out

The crawler's automated broken-image check also flagged the footer logo (`footerLogoIMG`) as
0×0 on every page. Verified with a direct HTTP request outside the browser: it's a real, valid
200 response, 612×208 PNG. That flag was an artifact of this sandboxed test browser's network
handling (TLS interception in this environment), not a live-site defect — noting it here so it
isn't chased as a real bug.
